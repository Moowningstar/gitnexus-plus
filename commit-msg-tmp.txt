Stop recommending --skip-fts, and stop writing a standing staleness prompt

Two changes, one measured finding behind them.

`--skip-fts` is no longer a default. It was one because the FTS extension
installs out-of-process and a confined process denies that. That reasoning
covers a narrow case and ignores the one operators actually hit:

  index has FTS + --skip-fts   179.22 s   full DB wipe + bulk COPY
  index has FTS, no flag         8.57 s   FTS fails to load, degrades cleanly
  index has no FTS + --skip-fts  8.25 s   changed=0, 39 rows preserved
  same, warm                     6.56 s

Disabling a search index the store already has forces GitNexus to rebuild the
whole graph store — a 21x penalty on the transition an operator is most likely
to hit, and the exact opposite of incremental. Letting FTS fail on its own
costs nothing: it prints a warning and indexes anyway. The flag stays available
for the case it was written for, where the extension file is absent and the
install itself fails.

The commands also now carry the measured cost, because "how expensive is a
refresh" is the question that decides whether to reach for --force at all.

AGENTS.md and CLAUDE.md no longer open with "Index stale? Run ...". That line
comes from GitNexus's own template, and the installed 1.6.12 has it bare. The
guidance to check `staleness.status` first and re-analyze only on behind or
diverged was added in ebbcd5b0 (2026-09-16), which is in the 1.6.13 release
candidates and in no stable release — so every agent reading the block treated
a capability reminder as a verdict on the index. It now reads as what it is:
documentation, with the refresh command attached.

The edit persists because `--index-only` suppresses the AGENTS.md rewrite
(analyze.js: `const willGenerateContext = !options.indexOnly && !options.skipAgentsMd`).
A full analyze without --index-only would regenerate it.
